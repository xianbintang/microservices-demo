## 为什么

Online Boutique 微服务演示配有完整的可观测性栈，但缺乏系统化的弹性测试。混沌工程将有助于验证故障条件下的系统弹性，在生产事故发生前发现薄弱环节，并建立对微服务架构的信心。

同时，混沌工程也是验证告警系统有效性的重要手段，通过主动注入故障来验证告警是否在正确时间触发、是否覆盖所有关键场景，从而确保告警系统的可靠性。

**重要前提**：在执行混沌实验之前，必须检查系统的告警覆盖度是否足够。如果告警覆盖不足，混沌实验引发故障时可能无法及时发现，导致问题扩大，甚至影响系统的可用性。因此，告警覆盖度检查是混沌工程的前置必要步骤。

**系统性实现**：本方案将通过 Claude Code skills 实现系统性的混沌工程流程，包括：
- 告警覆盖度检查
- 故障注入触发
- 实验监控和验证
- 告警验证
- 自我恢复验证
- 实验报告生成
- Runbook 整理

所有操作通过简单的 skill 命令完成，确保流程标准化和可重复性。

## 变更内容

- **前置步骤**：在混沌实验前进行告警覆盖度检查，确保关键场景都有告警覆盖
- 在 `monitoring` 命名空间部署 Chaos Mesh（或 Chaos Monkey）以提供故障注入能力
- 添加常见故障场景的混沌实验：
  - Pod 故障和重启
  - 网络延迟和丢包
  - 服务依赖故障（如 `adservice`、`recommendationservice`）
  - 资源耗尽（CPU、内存）
- 将混沌实验与可观测性栈集成（Grafana 大盘）
- 记录混沌实验工作流程和 runbooks
- 添加混沌实验防护机制，防止破坏性测试
- 使用混沌工程验证告警系统的完整性和有效性
- 建立告警验证流程，确保告警在正确时间触发
- 使用混沌工程验证系统自我恢复能力
- **通过 Claude Code skills 实现系统性流程**：所有混沌工程操作通过 skills 完成

## 能力

### 新增能力

- `chaos-alert-coverage-check`: 混沌实验前告警覆盖度检查，确保关键场景有告警覆盖
- `chaos-injection`: 用于测试弹性的故障注入能力
- `chaos-experiments`: 针对Online Boutique的预定义混沌实验场景
- `chaos-guardrails`: 混沌实验的安全机制和防护
- `chaos-integration`: 与可观测性栈集成以监控混沌运行
- `chaos-alert-validation`: 使用混沌工程验证告警系统有效性
- `chaos-self-healing-validation`: 使用混沌工程验证系统自我恢复能力
- `chaos-skills`: 通过 Claude Code skills 实现系统性混沌工程流程

### 修改的能力

- 无（无现有规格需求变更）

## 影响

- **基础设施**: 通过 Helm chart 在 `monitoring` 命名空间添加 Chaos Mesh 部署
- **可观测性**: 用于混沌实验结果和实验期间系统健康的新 Grafana 大盘
- **告警**: 告警覆盖度检查、混沌工程验证告警规则有效性和完整性
- **自我恢复**: 通过混沌工程验证 Kubernetes 和应用层面的自我恢复能力
- **Claude Code Skills**: 在 `.claude/skills/` 目录下创建混沌工程相关 skills
- **开发**: 用于 Chaos Mesh 配置的新 Helm values 文件
- **文档**: 混沌实验运行手册、告警验证指南、告警覆盖度检查指南、自我恢复能力验证指南和故障排除指南
- **依赖**: Chaos Mesh Helm chart
