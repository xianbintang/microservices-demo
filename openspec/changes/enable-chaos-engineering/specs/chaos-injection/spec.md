## 新增需求

### 需求: 故障注入能力
系统应提供故障注入能力用于测试微服务弹性，包括 Pod 故障、网络中断和资源限制。

#### 场景: Pod 终止注入
- **当** 混沌实验针对特定 Pod 进行终止操作
- **则** 指定的 Pod 被终止，Kubernetes 根据副本数重建它

#### 场景: 网络延迟注入
- **当** 混沌实验对服务应用网络延迟
- **则** 该服务的入站/出站流量按配置产生延迟（如 100ms、500ms）

#### 场景: 丢包注入
- **当** 混沌实验对网络流量应用丢包
- **则** 按配置的百分比（如 10%、50%）丢弃数据包

#### 场景: CPU 压力注入
- **当** 混沌实验对 Pod 应用 CPU 压力
- **则** 该 Pod 按配置的百分比和时长承受 CPU 负载

#### 场景: 内存压力注入
- **当** 混沌实验对 Pod 应用内存压力
- **则** 该 Pod 按配置的大小和时长消耗内存

### 需求: 混沌实验生命周期
系统应支持混沌实验的完整生命周期，包括创建、执行、监控和恢复。

#### 场景: 创建混沌实验
- **当** 运维人员创建混沌实验清单
- **则** 混沌控制器验证并应用实验配置

#### 场景: 执行混沌实验
- **当** 混沌实验启动
- **则** 对目标资源应用故障注入，持续指定时长

#### 场景: 监控混沌实验
- **当** 混沌实验运行中
- **则** 捕获系统指标和链路以评估影响

#### 场景: 从混沌实验恢复
- **当** 混沌实验完成或被中止
- **则** 移除注入的故障，受影响资源恢复正常状态
