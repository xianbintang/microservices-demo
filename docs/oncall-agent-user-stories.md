# 报警值守虚拟员工 — 用户故事

> 基于 4 个 Mock Skill（oncall-mock-demo / oncall-mock-realistic / oncall-mock-storm / oncall-mock-problem-centric）的深度分析，从 **Agent 能力**、**人机协同模式**、**演进路线** 三个维度整理。

---

## 一、Agent 核心能力清单

| # | 能力 | 说明 |
|---|------|------|
| 1 | **告警接收 & ACK** | 自动确认告警、临时屏蔽（30min）避免重复打扰 |
| 2 | **RCA 根因分析** | 分析过程可见（折叠面板），结论附带置信度（⭐⭐⭐~⭐⭐⭐⭐⭐） |
| 3 | **告警关联 & 归并** | 自动判断告警间关联性，合并到同一 Problem |
| 4 | **止损方案生成** | 生成方案 → 发审批卡片 → @值班人加急 |
| 5 | **止损执行** | 自动执行 kubectl 等操作，实时汇报进度 |
| 6 | **恢复验证** | 止损后自动验证指标，多轮对比，判定恢复/未恢复 |
| 7 | **纠偏 & 拆分** | 发现归并错误时自动修正，拆分为独立 Problem |
| 8 | **风暴检测** | 识别报警风暴（如 30s 内 5 条），自动聚合 + 静默 + 统一处理 |
| 9 | **并行处理** | 多条告警独立 ACK + 独立分析，不串行等待 |
| 10 | **静默管理** | 风暴期间静默报警规则，事后取消静默恢复正常报警 |
| 11 | **@值班人沟通** | 需要人工介入时主动 @ 值班人，不被动等待 |
| 12 | **接受指令 & 自我停止** | 值班人接管后 Agent 停止自主操作，移交控制权 |

## 二、四个场景的用户故事

### 场景 1️⃣：理想路径 — Agent 端到端自主处理（仅需审批）

> **作为**值班人，**我希望** Agent 能自主处理大部分告警流程，**以便**我只需在关键节点（审批）做决策，减少值班负担。

**验收标准（AC）：**

1. 告警到达 → Agent 自动 ACK + 屏蔽 + 启动分析
2. RCA 分析过程对值班人透明（可折叠查看分析步骤）
3. 分析完成后给出根因 + 置信度，自动创建 Problem
4. 新告警到达时能自动判断是否归并到已有 Problem
5. 生成止损方案 → 审批卡片 → 值班人一键批准/拒绝
6. 审批通过 → 自动执行止损 → 实时汇报进度
7. 止损完成 → 自动进行多轮恢复验证
8. 发现归并错误时能自动纠偏（拆分为新 Problem）
9. 全部恢复 → Problem 消除，更新告警卡片为"已恢复"

**关键交互时序：**

```
告警A到达 → Agent ACK → 分析中卡片（蓝色） → RCA完成卡片（绿色）
                ↓                                    ↓
告警B到达 → Agent ACK                    → 归并到 P-1001
                                                     ↓
                                         止损审批卡片（橙色） → @值班人
                ↓                                    ↓
告警C到达 → Agent ACK → 初判归并 P-1001   ← 值班人批准
                                                     ↓
                                         执行中卡片（蓝色） → 执行完成（绿色）
                                                     ↓
                                         恢复验证：A/B恢复 ✅，C未恢复 ❌
                                                     ↓
                                         纠偏：C从P-1001移除 → 创建P-1002
                                                     ↓
                                         P-1001消除 🎉
```

**对应 Skill：** `oncall-mock-demo`

### 场景 2️⃣：真实场景 — Agent 会犯错，人来纠偏

> **作为**值班人，**我希望**当 Agent 分析出错或方案不合理时，我能快速纠偏，Agent 能接受修正并继续工作，**以便**实现高效的人机协作而非单纯自动化。

**验收标准（AC）：**

| 幕 | Agent 行为 | 值班人行为 | 协同结果 |
|----|-----------|-----------|---------|
| Act 1: RCA 出错 | 判断为"TLS证书过期"（❌ 错误，置信度60%） | 纠偏："证书上周刚换，查下DNS" | Agent 接受 → 重新分析 → 定位 CoreDNS OOMKill ✅ |
| Act 2: 方案有风险 | 方案"删CoreDNS Pod"（⚠️ 仅剩1副本） | 拒绝："只剩1副本！改扩容3副本" | Agent 采纳修改 → 更新方案 → 重新审批 → 值班人批准 |
| Act 3: 分析卡住 | 新告警分析无果，无法定位根因 | Agent 主动求助 → 值班人："已知bug，静默" | Agent 执行静默 + 关联 Issue + 标记 Resolved |
| Act 4: 恢复不彻底 | 恢复验证未达标 | Agent 建议人工介入 → 值班人："我来接管" | Agent 停止自动操作，移交控制权 |

**关键人机协同模式：**

- **Agent 犯错 → 人纠偏 → Agent 修正**：Agent 给出错误 RCA，值班人指出正确方向，Agent 重新分析
- **Agent 方案不合适 → 人修改 → 重新审批**：审批被拒 → Agent 采纳修改 → 生成新方案 → 再次审批
- **Agent 卡住 → 主动求助**：分析无果时 Agent 不硬扛，主动 @值班人请求线索
- **Agent 识别边界 → 主动移交**：恢复不彻底时建议人工介入，值班人接管后 Agent 停止操作

**对应 Skill：** `oncall-mock-realistic`

### 场景 3️⃣：报警风暴 — 大量告警密集到达

> **作为**值班人，**我希望**当短时间内大量告警涌入时，Agent 能自动识别风暴、聚合分析、批量静默，**以便**我不被告警噪音淹没，可以聚焦在根因处理上。

**验收标准（AC）：**

1. 5 条告警在 30 秒内到达 → Agent 并行 ACK + 并行分析（不串行等待）
2. 触发风暴检测阈值 → 自动创建 Problem P-2001（风暴卡片）
3. 中止所有独立分析 → 分析卡片更新为"已中止，归并至P-2001"
4. 回到每条告警话题下通知已归并
5. 在 P-2001 话题内：静默所有报警规则 → 关联 RCA → @值班人建议止损
6. 值班人处理完 → Agent 取消静默 → 恢复验证
7. 4/5 恢复，1条未恢复 → 纠偏：发现独立根因（Redis缓存打满）→ 拆分 P-2002
8. P-2001 消除 + P-2002 在原告警话题下独立处理直到消除

**风暴模式核心逻辑：**

```
告警1 → ACK+分析 ─┐
告警2 → ACK+分析 ─┤
告警3 → ACK+分析 ─┤── 30s内5条 → 🌪️ 风暴触发！
告警4 → ACK       ─┤                ↓
告警5 → ACK       ─┘          创建 P-2001
                                    ↓
                              中止所有独立分析
                              每条告警话题下通知归并
                                    ↓
                   P-2001 话题内：静默 → RCA → 止损
                              → 取消静默 → 验证 → 纠偏
```

**对应 Skill：** `oncall-mock-storm`

### 场景 4️⃣：Problem-Centric 未来模式 — 群里只发 Problem 卡片

> **作为**值班人，**我希望**飞书群里不再有密密麻麻的告警卡片，Agent 足够智能后直接给我一张 Problem 卡片就够了，**以便**群消息的信噪比极高，我能快速把握全局。

**验收标准（AC）：**

1. Agent 后台收到 4 条告警 → **群里不发任何告警卡片** → 自动聚合分析
2. 群里只出现一张 Problem 卡片（P-3001），包含：关联告警数量、影响服务、根因初判、影响范围、告警明细（折叠）
3. 所有后续操作（RCA、审批、执行、验证）都在 Problem 话题下完成
4. 新告警到达 → 自动归并 → Problem 主卡片上关联告警数从 4 更新为 5（群级别不发新消息）
5. 全部恢复 → Problem 主卡片更新为"已消除"（绿色）
6. 话题内发送改进建议

**当前模式 vs 未来模式对比：**

| 维度 | 当前模式（场景1-3） | 未来模式（场景4） |
|------|-------------------|-----------------|
| 群消息 | 每条告警一张卡片 | **只有 Problem 卡片** |
| Agent 角色 | 接收告警 → 分析 → 通知 | **自主聚合 → 直接给结论** |
| 审批方式 | 群级别发审批卡片 | **话题内审批** |
| 进展更新 | 分散在各告警话题 | **全部集中在 Problem 话题** |
| 信噪比 | 中 | **极高** |

**核心理念：**

> 未来 Agent 足够强大后，值班人不需要看到每条原始告警。
> Agent 在后台自动聚合、分析、归因，然后**只向群里输出一张有明确结论的 Problem 卡片**。
> 所有后续操作（审批、执行、验证、消除）都在这个 Problem 的话题下完成。

**对应 Skill：** `oncall-mock-problem-centric`

## 三、Agent 交互设计原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **分析过程可见但不打扰** | 分析步骤放在折叠面板（`collapsible_panel`），值班人想看才展开 |
| 2 | **卡片原地更新** | 分析中（蓝色）→ 分析完成（绿色/橙色），不发新卡片，同一张卡片 update |
| 3 | **置信度标注** | 每次 RCA 都附带置信度（⭐⭐⭐ 60% ~ ⭐⭐⭐⭐⭐ 95%），让值班人判断可信度 |
| 4 | **话题内闭环** | 每条告警/Problem 的全部处理在其话题（thread）内完成，不污染群主对话 |
| 5 | **颜色语义一致** | 🔴红/🟠橙 = 告警/处理中，🔵蓝 = 分析中/执行中，🟢绿 = 完成/恢复，⚪灰 = 中止/静默，🟣紫 = 人工接管 |
| 6 | **主动通知而非等待** | 需要值班人介入时主动 @，不被动等 |
| 7 | **识别能力边界** | 分析不出来就主动求助，不硬编理由 |

## 四、Agent 演进路线图

4 个 Mock 场景代表 Agent 能力演进的 4 个阶段：

```
Stage 1: 理想路径          → Agent 能端到端处理，前提是问题简单明确
    ↓
Stage 2: 真实协作          → Agent 会犯错，但能接受纠偏、主动求助、识别边界
    ↓
Stage 3: 风暴处理          → Agent 能处理复杂场景：并行分析、风暴检测、批量静默、纠偏拆分
    ↓
Stage 4: Problem-Centric   → Agent 足够强，群里零告警噪音，只输出结论级 Problem
```

每个阶段都不是取代前一个，而是**能力叠加**：Stage 4 的 Agent 在底层仍然需要 Stage 1-3 的全部能力，只是把复杂性隐藏在了后台。

## 五、关键技术实现

| 技术点 | 实现方式 |
|--------|---------|
| 消息通道 | 飞书 Open API（`feishu_api` 模块：发消息、回复话题、更新卡片、@人） |
| 卡片格式 | 飞书 Interactive Card JSON 2.0，支持 `collapsible_panel`、按钮回调 |
| 话题模型 | 飞书 Thread（`reply_in_thread=True`），每条告警/Problem 的独立话题 |
| 审批机制 | 审批按钮 callback → 卡片原地更新为"已批准"/"已拒绝" |
| 加急通知 | `reply_at_message` 实现 @指定值班人（基于 open_id） |
| 卡片状态机 | 同一张卡片通过 `update_card` 在多个状态间转换（分析中→完成→中止） |
